1. Project Overview and Architecture

All three questions are implemented as one student admission portal made of three separate modules that share a single MySQL database named student_portal:

Module (folder)QuestionTechnologiesPurpose
Question1_FrontendQ1HTML5, CSS3, JavaScriptRegistration form with client-side validation
Question2_PHPQ2PHP 8 (PDO), MySQLAdmin panel: CRUD, file uploads, metadata
Question3_ServletQ3Java Servlet, JSP + JSTL, JDBC, TomcatSession-protected portal that lists profiles and streams files
databaseAllMySQL / MariaDBschema.sql – tables, constraints, demo data

Flow: a student fills in the registration form → JavaScript validates it → PHP saves it. The administrator logs in to the PHP panel to add, edit, view and delete students and to upload photos and documents. Each file is stored on disk under a random name and its metadata is stored in MySQL. Faculty log in to the Servlet portal, which reads the same database through JDBC and streams the same files through a Servlet.

  Browser ─► Question1_Frontend (HTML/CSS/JS) ── valid form ─► Question2_PHP/register.php
  Admin   ─► Question2_PHP  (Apache + PHP) ── PDO ──────────┐
                │ saves files to uploads/profiles|documents  ▼
                │                                    MySQL: student_portal
                ▼                                    (users, students, student_files)
  Faculty ─► Question3_Servlet (Tomcat) ── JDBC ────────────┘
                └─ FileDownloadServlet reads the files from Question2_PHP/uploads

Tools: XAMPP 8.2.12 (Apache, PHP 8.2, MariaDB 10.4), Tomcat 8.5.96, JDK 24, Connector/J 8.4.0, JSTL 1.2.5, jBCrypt 0.4.

2. QUESTION 1 – Student Registration Form (8 Marks)

Aim

To design a student admission registration form using HTML, style it with CSS (layout, colours, responsive design, styled inputs, buttons and error messages), and validate it on the client side using JavaScript (required fields, e-mail format and password strength).

Implementation

  • register.html – the form contains Full Name, Roll Number, Email, Mobile (optional), Course (drop-down), Password, Confirm Password, Profile Photo upload, ID-Proof upload (optional) and a declaration checkbox, with Submit and Reset buttons. It uses enctype="multipart/form-data" so files can be sent, and the novalidate attribute so that all validation is done by my own JavaScript.
  • css/style.css – colours are defined once as CSS variables; CSS Grid gives a two-column page and a two-column form; inputs have rounded borders and a focus ring; buttons have hover states; invalid fields turn red with a message underneath and valid fields turn green. Media queries switch to a single column on tablets and phones.
  • js/validation.js – one validator function per field. Fields are checked when the user leaves them and again while typing; a password-strength meter and checklist update on every key press. On submit, every field is validated and event.preventDefault() stops the form if anything is wrong.

Validation rules

form.addEventListener('submit', function (event) {
    const errors = [];

            errors.push(document.getElementById(fieldId + '-error').textContent);

    }

Every validator returns an error message or an empty string. validateField() writes the message with textContent (never innerHTML, so no HTML can be injected) and toggles the is-invalid / is-valid CSS classes. The source files contain inline comments explaining each part.

3. QUESTION 2 – PHP & MySQL Admin Panel (16 Marks)

Aim

To create PHP pages for the college admin panel that perform CRUD operations on student records in MySQL, handle uploads of profile images and documents, store the file metadata in MySQL linked to the student, display the uploaded files when a student is viewed, and validate file size and type while preventing files from being overwritten.

Implementation

PageFunction
login.php / logout.phpAdmin login with password_verify() and PHP sessions; logout destroys the session
dashboard.phpRead – statistics, search/filter and the list of all students
add_student.phpCreate – new student with optional photo and document
edit_student.phpUpdate – loads the record, validates and updates it
delete_student.phpDelete – confirmation page, then deletes the record and its files
view_student.phpView – full details, profile photo and all uploaded files

view_file.phpServes a stored file to the logged-in admin (view or download)

config/database.phpMySQL settings and the shared PDO connection

File upload handling and validation

  • Upload error codes are checked, and is_uploaded_file() confirms the file came from the form.
  • Size: profile photo ≤ 2 MB, document ≤ 5 MB.
  • Type: extension whitelist (photo: jpg, jpeg, png, webp; document: pdf, jpg, jpeg, png), dangerous double extensions such as shell.php.jpg are rejected, and the real MIME type is read from the file content with finfo.
  • No overwriting: every file is saved under a random 32-character name generated with random_bytes(), so two files with the same original name never replace each other.
  • Files go to uploads/profiles or uploads/documents; an .htaccess file blocks direct access and script execution there.

5. Database Schema

The script database/schema.sql creates the database student_portal, its three tables with primary keys, unique keys, a foreign key and check constraints, two demo login accounts and six sample students. Passwords are stored only as bcrypt hashes.

TableImportant columnsConstraints
usersid, username, full_name, password_hash, created_at, last_loginPK id; UNIQUE username
studentsid, name, roll_number, email, course, phone, date_of_birth, address, password_hash, created_at, updated_atPK id; UNIQUE roll_number; UNIQUE email
student_filesid, student_id, file_category, document_label, original_name, stored_name, file_path, file_type, file_size, upload_datePK id; FK student_id → students.id ON DELETE CASCADE; UNIQUE stored_name; CHECK category and size
database/schema.sql – file metadata table
CREATE TABLE student_files (
    id              INT             NOT NULL AUTO_INCREMENT,
    student_id      INT             NOT NULL,
    file_category   VARCHAR(20)     NOT NULL,
    document_label  VARCHAR(50)     NULL,
    original_name   VARCHAR(255)    NOT NULL,
    stored_name     VARCHAR(100)    NOT NULL,
    file_path       VARCHAR(255)    NOT NULL,
    file_type       VARCHAR(100)    NOT NULL,
    file_size       BIGINT UNSIGNED NOT NULL,
    upload_date     TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_files_stored_name UNIQUE (stored_name),
    CONSTRAINT fk_files_student FOREIGN KEY (student_id)
        REFERENCES students (id) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT chk_files_category CHECK (file_category IN ('profile', 'document')),
    CONSTRAINT chk_files_size CHECK (file_size > 0)
) ENGINE = InnoDB;

6. Security Measures

ThreatProtection used
SQL injectionPrepared statements in PHP (PDO) and Java (PreparedStatement)
Password theftbcrypt hashes (password_hash(), password_verify(), jBCrypt); same error for wrong user or password
Cross-site scriptinghtmlspecialchars(), <c:out>, textContent
Cross-site request forgeryToken in every PHP POST form, compared with hash_equals()
Malicious uploadsSize limits, extension whitelist, MIME check, random names, no-execute uploads folder
Path traversalrealpath() / toRealPath() and a check that the file stays inside uploads/
Unauthorised accessLogin sessions in PHP and Java, JSPs inside WEB-INF, .htaccess deny rules
Information leakageFriendly error pages; technical details only in the server logs

8. Conclusion

In this assignment I built a working student admission portal that combines a responsive HTML/CSS registration form with JavaScript validation, a PHP–MySQL admin panel for full CRUD operations and secure profile-image/document uploads, and a Java Servlet/JSP portal that reads the same database through JDBC and streams files through a Servlet. Uploaded files are validated by size, extension and real MIME type, stored under unique names so nothing is overwritten, and their metadata is linked to each student record. Prepared statements, password hashing, output escaping, CSRF tokens and session checks protect the system against common attacks and unauthorised access. Building it helped me understand how client-side scripting, server-side PHP, Java web components and a relational database work together in one application.
